- (decision) AD-1 Layered monolith, dependencies point inward only. Backend router->service->repository->model; frontend view->hook->api-client. Prevents: routers running SQL, components calling fetch, circular imports between siblings. Alternatives weighed: hexagonal (ports/adapters overhead unjustified at this size), single-file FastAPI app (no seam for the test layers the brief demands).
- (decision) AD-2 The OpenAPI schema FastAPI derives from app/schemas.py is the sole API contract authority; frontend mirrors it by hand in exactly one file src/api/types.ts. Prevents two components inventing different Todo shapes, and drift between addendum.md and code.
- (decision) AD-3 Wire format is camelCase JSON in both directions; Python stays snake_case internally via a Pydantic alias generator on a shared base schema. Prevents half the endpoints emitting created_at and half createdAt.
- (decision) AD-4 Every non-2xx response is {error, message} produced by centralized FastAPI exception handlers keyed to a small AppError hierarchy. Handlers never build error bodies inline; FastAPI's default {detail:...} (incl. 422 RequestValidationError) is remapped to VALIDATION_ERROR. Prevents two error envelopes on the wire.
- (decision) AD-5 The client always calls same-origin relative /api/*; the edge routes it (Vite dev-server proxy in dev, nginx in the frontend image for test/prod). No CORS middleware, no API URL baked into the bundle. Alternatives weighed: CORS + VITE_API_BASE_URL — rejected because Vite bakes env at build time, so one image could not serve dev and test.
- (decision) AD-6 All todo state and all mutations live in one useTodos hook implementing apply-optimistically -> call API -> rollback+surface error on failure. Components are presentational and receive callbacks. Prevents three divergent optimistic-update patterns and duplicated server state.
- (decision) AD-7 Ids are server-generated UUIDv4 strings. Optimistic creates render under a client-only temp key that is replaced by the server row on confirmation and never persisted or sent. Prevents duplicate rows and client-invented ids.
- (decision) AD-8 No migration tool. Schema is created by SQLModel.metadata.create_all() at startup; it is idempotent and additive-only. Any change that is not an additive nullable column requires deleting the SQLite file (documented as make db-reset). Prevents someone introducing Alembic or hand-written DDL. Alternative weighed: Alembic — rejected, user explicitly excluded migrations.
- (decision) AD-9 All SQL lives in app/repository.py; sessions come from one FastAPI dependency yielding a per-request Session. Services and routers never construct a Session or touch the engine. Prevents two session lifecycles and leaked connections.
- (decision) AD-10 Description validation (trim, 1..200 chars) is authoritative on the server in schemas.py; the client mirrors the limit from a single exported constant and rejects empty/whitespace before any network call (per FR-3). Prevents divergent limits between client and server.
- (decision) AD-11 Test layers are fixed by responsibility: pytest + httpx ASGITransport integration tests exercise every endpoint against a per-test temp SQLite file (no mocked DB); Vitest + Testing Library cover components and useTodos against a stubbed api client (no network); Playwright E2E runs only whole user journeys against the compose test profile. Prevents duplicated coverage and mock-heavy unit tests that prove nothing.
- (decision) AD-12 GET /api/health is the single liveness+readiness endpoint, returning {status, database} and doing a trivial DB round-trip. Both container HEALTHCHECKs and compose depends_on: service_healthy use it (frontend probes nginx root). Prevents divergent health semantics across containers.
- (decision) AD-13 The root Makefile is the only sanctioned entrypoint for humans and CI. GitHub Actions on pull_request calls make ci (lint, backend tests, frontend tests, build, E2E, coverage gate 70%). No workflow step reimplements a command. Prevents CI/local drift.
- (decision) AD-14 Environments are compose profiles over one docker-compose.yml: dev (bind mounts, hot reload, SQLite on a named volume) and test (built images, ephemeral SQLite, Playwright target). All configuration is env vars read once into a typed Settings object on the backend. Prevents per-environment compose files drifting apart.
